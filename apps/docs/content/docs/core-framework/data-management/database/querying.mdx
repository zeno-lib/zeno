## Clients

Both runtime clients and the Drizzle Kit preset read `DATABASE_URL` from the
environment unless you pass an explicit `connectionString` override. For local
and deployed connection strings, see
[Environment](/docs/core-framework/data-management/database#environment).

For deployed Supabase projects, prefer the
[Supabase connection pooler](https://supabase.com/docs/guides/database/connecting-to-postgres#server-side-poolers)
for serverless or autoscaling environments. The package sets `prepare: false` on
the underlying `postgres-js` pools so Supabase's transaction-mode pooler works.

Create the request-scoped Supabase client first, then bind it to
`createSupabaseDrizzle(...)`:

```typescript title="app/posts/route.ts"
import { createSupabaseDrizzle } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import * as schema from "{project}-db"

const supabase = await createClient()
const db = createSupabaseDrizzle({ schema, supabase })
```

Pass the imported schema module object to `createSupabaseDrizzle(...)`. Do not
build a new schema object inline for each request; reusing the module import
lets `@zeno-lib/db` reuse its underlying Postgres pools safely.

`createSupabaseDrizzle(...)` reads `DATABASE_URL` from the server environment in
this example. You only need `connectionString` when a script or service
intentionally connects to a different database URL.

## Query with RLS

`createSupabaseDrizzle(...)` returns a client you query directly **as the
signed-in Supabase user**, so `auth.uid()` resolves to that user and their RLS
policies apply. Query it exactly like a Drizzle client; each statement runs
inside an RLS-scoped transaction automatically:

```typescript title="app/posts/route.ts"
import { createSupabaseDrizzle } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import * as schema from "{project}-db"

const supabase = await createClient()
const db = createSupabaseDrizzle({ schema, supabase })

const myPosts = await db.select().from(schema.posts)
```

Awaiting a query calls `supabase.auth.getClaims()`, opens a transaction,
installs the verified JWT claims into transaction-local Postgres settings (so
`auth.uid()` and `auth.jwt()` work inside RLS policies), and runs the query as
the claims' role. Each awaited statement is its own transaction.

The RLS role is limited to `anon` or `authenticated`. Unknown role claims fall
back to `anon`, and `service_role` never runs through the request-scoped RLS
path.

`supabase` is required: `createSupabaseDrizzle(...)` throws at creation time if
you omit it (or pass `null`), so missing auth context fails loudly instead of
silently becoming an anon query.

### Relational queries

The [relational query API](https://orm.drizzle.team/docs/relations-v2) works the
same way once you pass a `relations` object (from Drizzle's `defineRelations`) to
`createSupabaseDrizzle(...)`:

```typescript title="app/posts/route.ts"
import { createSupabaseDrizzle } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import { defineRelations } from "drizzle-orm"
import * as schema from "{project}-db"

const relations = defineRelations(schema)
const supabase = await createClient()
const db = createSupabaseDrizzle({ relations, schema, supabase })

const myPosts = await db.query.posts.findMany()
```

### Multiple statements in one transaction

When you need several statements to share one atomic RLS transaction (for
example a read followed by a dependent write), use `db.transaction(...)`. Every
statement on the `tx` argument runs under the same claims and role:

```typescript title="app/posts/route.ts"
const created = await db.transaction(async (tx) => {
  const [post] = await tx
    .insert(schema.posts)
    .values({ title: "Hello" })
    .returning()
  await tx.insert(schema.auditLog).values({ postId: post.id })
  return post
})
```

Reach for `db.transaction` only when a single statement is not enough; one
direct statement is the common case.

## Use admin queries carefully

For trusted server work that should bypass user RLS, use `createAdminDrizzle(...)`.
It needs no Supabase client (it connects via `DATABASE_URL`) and is queried
directly:

```typescript title="{project}-db/src/seed.ts"
import { createAdminDrizzle } from "@zeno-lib/db"
import * as schema from "./schema"

const db = createAdminDrizzle({ schema })

await db.select().from(schema.posts)
```

The admin client does not switch roles. It runs as the role the client connects
as (the `postgres` role by default), which is not subject to RLS. That
connection role, not `service_role`, is what makes admin queries bypass policies.

`createAdminDrizzle(...)` is appropriate for seed scripts, webhooks, cron jobs,
admin tools, and background jobs. It should not be used for user-scoped reads or
writes.

## Lower-level clients

Most apps should use `createSupabaseDrizzle(...)`. If a shared library needs
explicit control over clients, use `createDrizzleClients(...)`:

```typescript lineNumbers
import { createDrizzleClients } from "@zeno-lib/db/clients"
import * as schema from "./schema"

const supabase = await createClient()
const clients = createDrizzleClients({ schema })
const admin = clients.getDrizzleSupabaseAdminClient()
const rls = clients.getDrizzleSupabaseClient(supabase)

const rows = await rls.runTransaction((rlsDb) =>
  rlsDb.select().from(schema.posts)
)

await clients.closeDrizzleSupabaseClients()
```

The lower-level RLS client takes a Supabase client and resolves verified claims
via `supabase.auth.getClaims()`. The DB package does not decode or trust raw JWT
strings.

## Pitfalls

- Do not import `@zeno-lib/db` runtime clients from Client Components or browser
  code.
- Do not use `createAdminDrizzle(...)` for user-scoped reads and writes.
- Do not pass raw access token strings or unverified session payloads to RLS
  helpers; `createSupabaseDrizzle(...)` accepts a Supabase client only.
- Do not create fresh schema object literals per request.
- Do not run reads or writes through `createAdminDrizzle(...)` when you expect
  RLS policies to apply; it bypasses them. Use `createSupabaseDrizzle(...)` (its
  direct queries and `db.transaction(...)`) for user-scoped, RLS-enforced work.
