## Clients

`@zeno-lib/db` exports five client factories. Each takes an optional Drizzle
config (`{ relations?, logger?, casing? }`) plus an optional `connectionString`
and `requirePooler`. Without `connectionString`, it reads
`SUPABASE_DATABASE_URL` from the environment. For local and deployed
connection strings, see
[Environment](/docs/core-framework/data-management/database#environment).

| Factory | Runs as | Use for |
|---|---|---|
| `createAuthClient(supabase, config?)` | the signed-in user (`anon`/`authenticated`) | per-request, RLS-enforced reads and writes |
| `createAnonClient(config?)` | `anon` | unauthenticated, RLS-enforced reads |
| `createServiceClient(config?)` | `service_role` (bypasses RLS) | trusted server work that needs `service_role` |
| `createSupabaseClient(accessToken, config?)` | the token's role (`anon`/`authenticated`) | RLS work when you already hold the verified, decoded claims |
| `createAdminClient(config?)` | the `postgres` connection role (bypasses RLS) | seeds, webhooks, cron, background jobs |

The RLS clients (`createAuthClient`, `createSupabaseClient`, `createAnonClient`)
clamp a user token's role to `anon` or `authenticated`. A forged or unexpected
role claim falls back to `anon`, and `service_role` is reachable only through the
explicit `createServiceClient`, never from a JWT.

For deployed Supabase projects, prefer the
[Supabase connection pooler](https://supabase.com/docs/guides/database/connecting-to-postgres#server-side-poolers)
for serverless or autoscaling environments. The package sets `prepare: false` on
the underlying `postgres-js` pools so Supabase's transaction-mode pooler works.
The package caches pools per `(kind, connectionString)`, and `close()` is
reference-counted, so a handle releases only its share of the shared pool.

## Query with RLS

Create the request-scoped Supabase client first, then bind it to
`createAuthClient(...)`. You query the returned client directly, and each query
runs **as the signed-in Supabase user**, so `auth.uid()` resolves to that user
and RLS policies apply:

```typescript title="app/posts/route.ts"
import { createAuthClient } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import * as schema from "{project}-db"

const supabase = await createClient()
const db = createAuthClient(supabase)

const myPosts = await db.select().from(schema.posts)
```

Awaiting a query calls `supabase.auth.getClaims()`, opens a transaction,
installs the verified JWT claims into transaction-local Postgres settings (so
`auth.uid()` and `auth.jwt()` work inside RLS policies), and runs the query as
the claims' role. Each awaited statement is its own transaction unless it runs
inside `db.transaction` (below), and the client re-resolves claims for **every**
transaction, so a single client always reflects the live session.

`createAuthClient(...)` does not take a `schema`. The client resolves types from
the tables you reference in the query itself. Pass a `relations` object only when
you want the relational query API (see below).

### Relational queries

The [relational query API](https://orm.drizzle.team/docs/relations-v2) works the
same way once you pass a `relations` object (from Drizzle's `defineRelations`) to
the factory. Build the `relations` object once at module scope, not per request:

```typescript title="app/posts/route.ts"
import { createAuthClient } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import { defineRelations } from "drizzle-orm"
import * as schema from "{project}-db"

const relations = defineRelations(schema)
const supabase = await createClient()
const db = createAuthClient(supabase, { relations })

const myPosts = await db.query.posts.findMany()
```

### Multiple statements in one transaction

When you need several statements to share one atomic RLS transaction (for
example a read followed by a dependent write), use `db.transaction(...)` and run
each statement on its `tx` argument, which runs under the same claims and role:

```typescript title="app/posts/route.ts"
const created = await db.transaction(async (tx) => {
  const [post] = await tx
    .insert(schema.posts)
    .values({ title: "Hello" })
    .returning()
  await tx.insert(schema.auditLog).values({ postId: post.id })
  return post
})
```

Parallel reads work the same way. Pass `tx` to each query function, and they
share one `begin`, one claims setup and one `commit` instead of opening a
transaction each:

```typescript title="app/posts/[id]/page.tsx"
const [post, comments] = await db.transaction((tx) =>
  Promise.all([selectPost(tx, id), selectComments(tx, id)])
)
```

#### Reads that cannot take `tx`

Some reads sit behind code that has no way to receive `tx`, such as a query
factory that calls a server action or a `defineQuery`, which builds its own
client with `getRequestDb()` (see below). For those, a statement on `db` itself, awaited
while the callback runs, joins the transaction too:

```typescript title="app/posts/[id]/page.tsx"
const db = await getRequestDb()
await db.transaction(() =>
  // The server actions behind these queries reach the transaction through
  // getRequestDb(), not through tx.
  Promise.all([
    queryClient.prefetchQuery(postQueryOptions(id)),
    queryClient.prefetchQuery(commentsQueryOptions(id)),
  ])
)
```

This goes through the async context, so it covers only the same client, and
only while the callback runs: another client keeps its own transactions, and a
statement started after the callback ends opens its own. Pass `tx` whenever you
can, because then the code shows which statements share the transaction.

Either way, the statements run one after another on one connection. A
`db.transaction` inside another one is a savepoint of it, so never run two of
those in parallel. Postgres aborts a transaction at its first failed statement,
so the statements after it fail too, and `db.transaction` rejects with that
first error even when the callback caught it, as `prefetchQuery` does.

Use `db.transaction` only when a single statement is not enough; one direct
statement is the common case.

## Request-scoped client for Next.js

`@zeno-lib/db/next` wraps `createSupabaseClient` for the App Router. Create one
module per app (not a `"use server"` file) that binds it to your Supabase server
client and relations:

```typescript title="{project}-db/src/server-db.ts"
import { createRequestDb } from "@zeno-lib/db/next"
import { createClient } from "@zeno-lib/supabase/next-server"
import { relations } from "./relations"

export const {
  defineAction,
  defineFormAction,
  defineQuery,
  getRequestContext,
  getRequestDb,
} = createRequestDb({ relations, supabase: () => createClient() })
export { UnauthenticatedError } from "@zeno-lib/db/next"
```

`getRequestContext()` verifies the cookie session with `auth.getClaims()` once
per server render, because React's `cache` wraps it. It returns
`{ claims, db }`, where `db` runs as the caller with the **whole** verified
claims object installed. It never falls back to `anon`. Without a verified
`sub`, it throws `UnauthenticatedError`. `getRequestDb()` returns just the `db`.

`defineAction(schema, handler)` turns each server action into one line. The
returned async function parses its argument with `schema.parse`, then calls
`handler(db, input, context)`:

```typescript title="app/posts/actions.ts"
"use server"

import { defineAction } from "{project}-db/server-db"
import { z } from "zod"
import { deletePost, insertPost } from "./queries"

export const deletePostAction = defineAction(z.number().int(), deletePost)

// Stamp authorship from the verified claims, never from an argument.
export const createPostAction = defineAction(
  z.object({ title: z.string().min(1) }),
  (db, input, { claims }) => insertPost(db, { ...input, userId: claims.sub })
)
```

An action never resolves to `undefined`. When the handler does (a `findFirst`
that matches no row, for example), the action resolves to `null`. TanStack
Query rejects a query whose function resolves to `undefined`, so a query
function can return a read action's result as it is, typed `T | null`.

When being signed out is a valid answer (in a permission check, say), catch the
named error instead:

```typescript
const db = await getRequestDb().catch((error: unknown) => {
  if (error instanceof UnauthenticatedError) return null
  throw error
})
```

### Returning validation errors to a form

In production, Next.js replaces a thrown server-action error's message with a
generic one, so the `ZodError` that `defineAction` throws on bad input reaches
the browser without its issues. For an action a form submits, use
`defineFormAction`, which `createRequestDb` returns next to `defineAction`. It
takes the same arguments and runs in the same order (validate, then resolve
the session, then call the handler), but it resolves to an `ActionResult`
instead of throwing on invalid input:

```typescript
type ActionResult<T> =
  | { ok: true; data: T }
  | {
      ok: false
      error: {
        fieldErrors: Record<string, string[]> // "address.city", "owners[0].share"
        formErrors: string[] // issues with no path
      }
    }
```

Field keys are the names TanStack Form registers fields under: object keys
joined with `.`, array indices in brackets. Schema issues come back this way,
and so does a `FieldValidationError` thrown from the handler, for a check only
the database can make:

```typescript title="app/teams/actions.ts"
"use server"

import { isConstraintViolation } from "@zeno-lib/db/errors"
import { FieldValidationError } from "@zeno-lib/db/next"
import { defineFormAction } from "{project}-db/server-db"
import { z } from "zod"
import { insertTeam } from "./queries"

export const createTeamAction = defineFormAction(
  z.object({ name: z.string().min(2), slug: z.string().min(3) }),
  async (db, input, { claims }) => {
    try {
      return await insertTeam(db, { ...input, userId: claims.sub })
    } catch (error) {
      if (isConstraintViolation(error, ["teams_slug_key"])) {
        throw new FieldValidationError({ slug: "That slug is taken" })
      }
      throw error
    }
  }
)
```

Everything else still throws: `UnauthenticatedError`, a database error, a bug.
A `FieldValidationError` thrown inside `db.transaction(...)` rolls the
transaction back before `defineFormAction` converts it. On the client,
`submitAction` from `@zeno-lib/forms` writes the result onto the form; see
[Server actions](/docs/feature-modules/components/forms/examples#server-actions).

`defineAction` still throws. Use it for an action whose errors no form renders
(a delete button, a toggle).

### Reads through a query route

The browser runs server actions **one at a time**: Next.js queues each call
until the one before it settles. That suits a write, but a screen whose cards
each read through an action waits for every read in turn, and each one pays
the round trip to the server and on to the database. Serve reads from a route
instead, where each call is its own request and they run in parallel.

`defineQuery`, which `createRequestDb` returns next to `defineAction`, takes
the same arguments and behaves the same way: parse, verify the session, call
the handler, resolve `undefined` to `null`. The difference is where it lives:
export it from a module **without** `"use server"`, and gather those exports
into the map a query route serves:

```typescript title="app/posts/queries.ts"
import "server-only"

import { defineQuery } from "{project}-db/server-db"
import { z } from "zod"
import { selectPosts } from "./db-queries"

export const selectPostsQuery = defineQuery(
  z.object({ authorId: z.string() }),
  selectPosts
)
```

```typescript title="app/api/queries/[query]/route.ts"
import { createQueryRoute } from "@zeno-lib/query/query-route"
import * as queries from "@/app/posts/queries"

export const { POST } = createQueryRoute(queries)
```

The browser side, `createQueryCaller`, and the server prefetch are on the
[Queries](/docs/core-framework/data-management/queries#reads-through-a-query-route)
page. Every entry in the map is a public endpoint, exactly like a server action:
`defineQuery` checks the session and RLS authorizes the rows, and the schema
bounds what a caller can ask for. `import "server-only"` makes a client import
of the module fail the build instead of bundling your database client.

## Other RLS clients

When you already hold the verified, decoded claims (for example from a prior
`supabase.auth.getClaims()` call), skip the `getClaims()` call each transaction
makes with
`createSupabaseClient(accessToken, config?)`. It accepts a decoded
`SupabaseToken` (the `role` and `sub` claims), not a raw JWT string, and does not
re-verify it:

```typescript title="app/posts/route.ts"
import { createSupabaseClient } from "@zeno-lib/db"
import * as schema from "{project}-db"

const db = createSupabaseClient({ role: "authenticated", sub: userId })

const myPosts = await db.select().from(schema.posts)
```

For unauthenticated, RLS-enforced reads, use `createAnonClient()`, which runs
every query as `anon`:

```typescript
import { createAnonClient } from "@zeno-lib/db"

const db = createAnonClient()
```

Prefer `createAuthClient` when you have a Supabase client. It resolves and
verifies claims through `auth.getClaims()` before every transaction, so it
always reflects the live session.

## Use admin and service queries carefully

For trusted server work that should bypass user RLS, use `createAdminClient(...)`.
It needs no Supabase client (it connects via `SUPABASE_DATABASE_URL`), and you
query it directly:

```typescript title="{project}-db/src/seed.ts"
import { createAdminClient } from "@zeno-lib/db"
import * as schema from "./schema"

const db = createAdminClient()

await db.select().from(schema.posts)
```

`createAdminClient(...)` does not switch roles. It runs as the role the client
connects as (the `postgres` role by default), which is not subject to RLS. That
connection role, not `service_role`, is what makes admin queries bypass policies.

`createServiceClient(...)` instead runs every statement as `service_role`, which
bypasses RLS through Supabase's `BYPASSRLS` grant. It is the only path to
`service_role`; use it when trusted work needs that role rather than the
`postgres` connection role:

```typescript
import { createServiceClient } from "@zeno-lib/db"
import * as schema from "./schema"

const db = createServiceClient()

await db.select().from(schema.posts)
```

Use either for seed scripts, webhooks, cron jobs, admin tools, and background
jobs. Never use them for user-scoped reads or writes.

## Query helpers

`@zeno-lib/db/query` covers the PostgREST conveniences Drizzle has no
equivalent for.

`one(rows)` is the equivalent of `.single()`. It returns the row and throws
unless there is exactly one. `maybeOne(rows)` is the equivalent of
`.maybeSingle()`. It returns the row, or `undefined` when there is none, and
throws when there are several.

```typescript
import { maybeOne, one } from "@zeno-lib/db/query"

const post = one(await db.insert(posts).values(input).returning())
const draft = maybeOne(await db.select().from(posts).where(eq(posts.id, id)))
```

`excludedSet(table, values, { target? })` builds the `set` that makes
`onConflictDoUpdate` behave like `.upsert()`. It writes every column the caller
supplied back from `excluded`, under its database name.

```typescript
import { definedValues, excludedSet } from "@zeno-lib/db/query"

const values = definedValues(input)
await db
  .insert(contacts)
  .values(values)
  .onConflictDoUpdate({ target: contacts.id, set: excludedSet(contacts, values) })
```

It skips a key holding `undefined`, because Drizzle leaves it out of the insert
and `excluded.<col>` would be the column default, overwriting the stored value.
It never writes back the conflict target (`"id"` unless `target` names other
column keys). When the caller supplied nothing else, the set falls back to
`id = excluded.id`, because Drizzle refuses an empty set while building the
statement. A table without that column (a junction keyed by its foreign keys)
gets an empty set; use `onConflictDoNothing` there.

### Syncing a parent's rows

A form that edits a parent with its child rows, such as an order and its lines,
sends back the whole list. `syncRows(db, table, { parent, rows })` makes that
list the parent's rows: it removes the stored rows that left the list, updates
the ones still in it and inserts the new ones. It resolves to the saved rows in
input order, so the form can take up the new ids.

```typescript title="app/orders/queries.ts"
import { one, syncRows } from "@zeno-lib/db/query"

export const updateOrder = (db: Db, { id, lines, ...values }: OrderInput) =>
  db.transaction(async (tx) => {
    const order = one(
      await tx.update(orders).set(values).where(eq(orders.id, id)).returning()
    )
    const saved = await syncRows(tx, orderLines, {
      parent: { orderId: id },
      rows: lines,
    })
    return { ...order, lines: saved }
  })
```

`parent` holds the columns that make a row the parent's. The sync reads, updates
and removes only the rows that match all of them, and writes them onto every
row, so a row leaves them out and can't land under another parent. A `null`
value matches `null`, but at least one value must not be `null`: a parent that
isn't saved yet would otherwise reach every orphaned row in the table.

By default, rows are told apart by their `id`; pass `id` to name another column.
A row without an id is new. A row whose id the parent doesn't hold, because it
belongs to another parent or was deleted since the form loaded it, is inserted
as a new row, so a sync never writes another parent's row. When the id column
has no default (`primaryId("assigned")`), the caller assigns ids: a new row
keeps its id, and one another row already holds fails on the primary key.

The form and the sync agree on what a row is through
[`ownedRows`](/docs/core-framework/data-management/schemas#edit-a-parents-rows-as-a-list),
which `syncRows` takes in place of the table. Its `parent` must then name
exactly the descriptor's parent columns:

```typescript
await syncRows(tx, orderLinesOfOrder, { parent: { orderId: id }, rows: lines })
```

A junction table, or any table whose rows are told apart by what they point at,
takes `key`, the natural key columns within the parent. Each row carries them,
since a missing one would be stored as the column default and never match
again, and a `null` key part matches a stored `null`:

```typescript
await syncRows(tx, postsTags, {
  key: ["tagId"],
  parent: { postId },
  rows: tagIds.map((tagId) => ({ tagId })),
})
```

- The rows that left the list are removed first, then the kept rows are
  updated, then the new rows are inserted. A row the user removes and adds back
  doesn't hit a unique index, and neither does a new row that takes a value a
  kept row gives up. A kept row that points at a new row through a foreign key
  needs that key to be `deferrable initially deferred`, since the new row
  doesn't exist yet when the kept row is updated.
- An update sets only the columns a row carries and changes, and a property
  holding `undefined` keeps its stored value. A kept row with nothing changed is
  returned as it is, unwritten, so its `updated_at` stays put.
- An empty list removes every row of the parent.
- Two rows with the same key reject before anything is written. Next redacts
  that error in production, so reject duplicates in the form's schema too, where
  the user sees them on the field.
- It runs in `db.transaction`, which is a savepoint inside a `tx`. A failure
  undoes every write the sync made, and nothing else.

The rows that left the list are deleted. To soft-delete or unlink them instead,
or to delete only the ones nothing else references, pass `remove`. It gets the
transaction and the removed rows, and runs before any update or insert:

```typescript
await syncRows(tx, orderLines, {
  parent: { archivedAt: null, orderId },
  remove: (tx, removed) =>
    tx
      .update(orderLines)
      .set({ archivedAt: new Date() })
      .where(inArray(orderLines.id, removed.map(({ id }) => id))),
  rows: lines,
})
```

With `archivedAt: null` in `parent`, archived rows stay out of the sync, and new
rows are written unarchived. An archived row still holds its key, so make the
unique index partial, or a removed key can't come back:

```typescript
uniqueIndex()
  .on(table.orderId, table.product)
  .where(sql`${table.archivedAt} is null`)
```

The sync reads the parent's rows before it writes, so two syncs of one parent
at the same time can both insert the same new row. A unique index on the parent
and key columns makes the second one fail instead. Add `.nullsNotDistinct()`
when a key part is nullable, because Postgres otherwise treats two `NULL`s as
different and lets both rows in. Updating the parent row first in the same
transaction, as `updateOrder` does, makes the second sync wait for the first to
commit.

A parent can hold thousands of rows, such as the grants on a shared folder. The
removals and the inserts go many rows to a statement, split to stay under
Postgres's limit of 65,535 bind parameters, so saving thousands of new grants
or revoking thousands takes a few statements. Each kept row that changed is
still one update. To change thousands of kept rows at once, use `insert` with
`onConflictDoUpdate`.

A trigger can rewrite the rows the sync keeps. Say a team's members hold shares
that must sum to 1, and a delete trigger hands a leaving member's share to the
members left. The sync compares the listed rows with the parent's rows as they
stand after the removal, so a member whose listed share is the one she started
with is written back too, and the save ends with the listed shares. That costs
one more read of the parent's rows, and only when the sync removed something.
`remove` gets the same treatment: a change it makes to the rows left counts. A
kept row that the removal deleted, through a cascade or a trigger, rejects the
sync rather than coming back as a new row.

A trigger that an update or an insert fires runs after that comparison, so what
it writes to the other rows stays, and the rows the sync returns don't show it:
each is what its own statement returned. Read the parent's rows again after the
sync when such a trigger exists.

Between its statements, the sync leaves the rows in states the save doesn't end
in, such as shares that sum to 0.8 once a member is removed. Check a rule across
rows in a deferred constraint trigger, which runs at commit:

```sql
create constraint trigger team_members_shares_sum
  after insert or update or delete on team_members
  deferrable initially deferred
  for each row execute function check_team_members_shares();
```

## Errors

Drizzle wraps every driver error in a `DrizzleQueryError` whose own `code` is
`undefined`, so `error.code === "23505"` is always false. `@zeno-lib/db/errors`
extracts the postgres.js error:

```typescript
import { isConstraintViolation, SqlState, toPostgresError } from "@zeno-lib/db/errors"

try {
  await db.insert(contacts).values(row)
} catch (error) {
  if (isConstraintViolation(error, ["contacts_email_key"], { code: SqlState.uniqueViolation })) {
    return { error: "That email is already a contact" }
  }
  throw error
}
```

`toPostgresError(error)` returns the `PostgresError` (with `code`,
`constraint_name`, `detail`, …) or `undefined`. It only returns errors the
server sent: one postgres.js raises itself, such as a closed connection or a
query cancelled before it was sent (`57014`), gives `undefined`. A
`PostgresError` you build in a test needs a SQLSTATE `code` and a
`severity_local`, like the real one. `isConstraintViolation(error,
constraints?, { code? })` returns it only for an integrity-constraint violation
(any class `23` code unless `code` narrows it) and, when you pass
`constraints`, only for one of those. `SqlState` names the codes an application
usually branches on.

## Testing against the database

Suites that share one local database, and run in parallel with each other and
with your end-to-end tests, must not commit what they write: a committed row
changes what every other suite counts. `@zeno-lib/db/testing` has three helpers
for those tests. They throw instead of calling `expect`, so any test runner can
use them.

```typescript
import { SqlState } from "@zeno-lib/db/errors"
import { expectPostgresError, expectRlsDenied, rollBackAfter } from "@zeno-lib/db/testing"

it("rejects a second contact with the same email", () =>
  rollBackAfter(db, async (tx) => {
    await tx.insert(contacts).values(ada)

    const error = await expectPostgresError(
      tx.insert(contacts).values(ada),
      SqlState.uniqueViolation
    )
    expect(error.constraint_name).toBe("contacts_email_key")
  }))
```

- `rollBackAfter(db, run)` runs `run` in a transaction that always rolls back,
  and resolves to what `run` returned. Nothing it writes is visible outside the
  transaction, and nothing needs cleaning up, whatever the rows cascade into.
  Only statements sent through `tx` are in it: a write through another client,
  such as a module-level `admin`, commits.
  `run` gets the same transaction type `db.transaction` hands you, relations
  included, and an error it throws is rethrown. On a `tx`, it runs in a
  savepoint.
- `expectPostgresError(query, code)` resolves to the `PostgresError` when the
  query fails with that SQLSTATE, so you can check its `constraint_name` or
  message. It rejects when the query succeeds, which a bare `try`/`catch` misses,
  and when it fails with another code. Pass the query, or a function that starts
  it.
- `expectRlsDenied(query)` is the same check for `insufficient_privilege`
  (`42501`): a write a row-level security policy or a missing grant refused. A
  `select` that RLS filters doesn't fail, it returns fewer rows, so assert on
  those instead.

<Callout type="warn">
A failed statement aborts the transaction it ran in, and every later statement
in it fails too. Make the failing query the last statement in `rollBackAfter`,
or run it in a savepoint with `tx.transaction(...)`.
</Callout>

## Pitfalls

- Do not import `@zeno-lib/db` runtime clients from Client Components or browser
  code.
- Do not use `createAdminClient(...)` or `createServiceClient(...)` for
  user-scoped reads and writes; they bypass RLS. Use `createAuthClient(...)`,
  `createSupabaseClient(...)`, or `createAnonClient(...)` for RLS-enforced work.
- Do not pass a raw access token string to `createSupabaseClient(...)`; it
  expects a verified, decoded `SupabaseToken` and does not re-verify it. Prefer
  `createAuthClient(...)`, which verifies claims itself.
- Do not feed a user-supplied token to `createServiceClient(...)`. It clamps
  nothing and grants `service_role`; it is a trusted backend decision.
- Do not put `"use server"` in the module that calls `createRequestDb`, and do
  not export `getRequestDb` from a `"use server"` file: every export there is a
  public endpoint.
- Do not build a fresh `relations` object literal per request. Pass a stable
  `relations` object, or a cached client built without relations may be reused.
