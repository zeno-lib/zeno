Each table lives in its own file under `{project}-db/src/schemas/`, where
`{project}` is your workspace name. Drizzle Kit reads the exported tables when it
generates migrations, and Drizzle uses the same exported table objects when you
write queries.

The example below is a complete table definition. It is here to show how the
pieces fit together; every helper it uses (`table`, `primaryId`, `authUserId`,
`auditColumns`, and the owner policies) is documented in detail under
[Schema helpers](#schema-helpers) further down.

```typescript lineNumbers title="{project}-db/src/schemas/posts.ts"
import {
  auditColumns,
  authenticatedOwnerInsertPolicy,
  authenticatedOwnerSelectPolicy,
  authUserId,
  primaryId,
  table,
} from "@zeno-lib/db/schema"
import { text } from "drizzle-orm/pg-core"

export const posts = table(
  "posts",
  {
    id: primaryId("uuid"),
    title: text().notNull(),
    // Supabase owns auth.users; this reference links your table to the signed-in user.
    // `notNull` because the owner policies below key on it.
    userId: authUserId({ notNull: true }),
    // created_at, updated_at, created_by, and updated_by, from @zeno-lib/db/schema.
    ...auditColumns(),
  },
  (t) => [
    authenticatedOwnerSelectPolicy("posts_owner_select", t.userId),
    authenticatedOwnerInsertPolicy("posts_owner_insert", t.userId),
  ]
)
```

Re-export every table from a single `{project}-db/src/schema.ts` barrel. That
barrel is what the [Drizzle Kit config](/docs/core-framework/data-management/database/migrations)
reads, what your queries import to reference tables, and what feeds
`defineRelations(...)` for the relational query API when
[querying](/docs/core-framework/data-management/database/querying):

```typescript title="{project}-db/src/schema.ts"
export * from "./schemas/posts"
// export * from "./schemas/comments"
```

Keeping this shape in TypeScript has a few practical benefits: the table is the
source of truth for migrations, query types are inferred from the same object,
common columns can be reused as code, and validation schemas can be derived from
the table later. For that next layer, see
[Schemas](/docs/core-framework/data-management/schemas).

## Schema helpers

Everything below is exported from `@zeno-lib/db/schema`, and all of it is just
convenience utilities, none of it is required. You can always define tables,
columns, and RLS policies with Drizzle's own primitives directly whenever you
need something these utils don't cover. The module simply gathers the common
cases (table builders, reusable columns, RLS policies, and curated re-exports of
the Drizzle and Supabase primitives) behind one Zeno-owned entrypoint so you
don't import them from several packages.

### Anatomy of a table

Every helper slots into one of three places in a table definition. Keep this
shape in mind. Each helper below is tagged with the slot it belongs to.

```typescript
export const posts = table(   // ① table builder: wraps the table, toggles RLS
  "posts",
  {                           // ② columns map: primary key, columns, column builders
    id: primaryId("uuid"),
    userId: authUserId({ notNull: true }),
    ...auditColumns(),
  },
  (t) => [                    // ③ extra callback: indexes, constraints, RLS policies
    authenticatedOwnerSelectPolicy("posts_owner_select", t.userId),
  ]
)
```

- **① table builder**: wraps the columns and the extra callback.
- **② columns map**: spread a group (`...auditColumns()`) or assign to a key
  (`userId: authUserId({ notNull: true })`).
- **③ extra callback**: receives the built columns `t` and returns indexes,
  constraints, and RLS policies.

Each entry below shows the Drizzle it expands to and the SQL that Drizzle Kit
generates from it.

### Table builders

_Slot ①: wraps the whole table._ Both map camelCase TypeScript keys to
snake_case database identifiers, so `userId` becomes `user_id`.

`table(name, columns, extra?)` builds a Postgres table with **RLS enabled**. Use
it for application-owned tables:

```typescript
table("posts", { /* columns */ }, (t) => [ /* policies */ ])
```

```sql
CREATE TABLE "posts" ( /* columns */ );
ALTER TABLE "posts" ENABLE ROW LEVEL SECURITY;
```

`unsecureTable(name, columns, extra?)` is the same builder **without** the
`ENABLE ROW LEVEL SECURITY` line. Use it only for intentionally unprotected
tables such as seed or reference data.

`schema(name)` builds a non-public schema that gives you the same two builders,
with the same casing and the same RLS default:

```typescript
const billing = schema("billing")

billing.table("invoices", { /* columns */ })        // RLS enabled
billing.unsecureTable("rates", { /* columns */ })   // no RLS
```

```sql
CREATE SCHEMA "billing";
CREATE TABLE "billing"."invoices" ( /* columns */ );
ALTER TABLE "billing"."invoices" ENABLE ROW LEVEL SECURITY;
CREATE TABLE "billing"."rates" ( /* columns */ );
```

It is otherwise Drizzle's `pgSchema`, so `existing()`, `enum()`, `sequence()`,
`view()` and `materializedView()` all work as they do there. Reach for Drizzle's
`pgSchema` directly only when you want a schema whose column names come
verbatim from their TypeScript keys.

### Primary keys

_Slot ②: assign to a key in the columns map._ `primaryId(kind)` covers the three
ways a primary key gets its value. Each kind emits the column Supabase itself
creates for that choice, so a table you started in the dashboard and a table you
started here describe the same thing. The column is named `id`.

`primaryId("sequential")` is an auto-incrementing key. It is what the dashboard
gives a new table when you accept its defaults, so it is also what you get from
a bare `primaryId()`:

```typescript
id: primaryId("sequential")
```

```sql
"id" bigint PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY (
  sequence name "posts_id_seq" INCREMENT BY 1
  MINVALUE 1 MAXVALUE 9223372036854775807 START WITH 1 CACHE 1
)
```

`bigint` rather than `integer` because `integer` stops at 2.1 billion rows, and
`by default` rather than `always` because `always` refuses ids you supply
yourself, which breaks seeds and upserts.

`primaryId("uuid")` is a random UUID key, the dashboard's UUID option:

```typescript
id: primaryId("uuid")
```

```sql
"id" uuid PRIMARY KEY DEFAULT gen_random_uuid()
```

`primaryId("assigned")` is a key your application supplies, such as a
human-readable invoice number. It has no default and no identity, so you always
pass a value:

```typescript
id: primaryId("assigned")
```

```sql
"id" varchar PRIMARY KEY
```

#### Configuring a primary key

`primaryId` takes the kind and nothing else. To rename the column or change how
the value is generated, call the helper behind the kind and pass options.

| Kind | Helper | Options |
|---|---|---|
| `"sequential"` | `sequentialPrimaryId()` | `name`, `type`, `mode`, `generated` |
| `"uuid"` | `uuidPrimaryId()` | `name`, `defaultRandom` |
| `"assigned"` | `assignedPrimaryId()` | `name`, `length` |

`uuidPrimaryId({ defaultRandom: false })` skips the `gen_random_uuid()` default,
for a table whose id comes from somewhere else. A public table mirroring
`auth.users` is the usual case: the row's id *is* the auth user's id, so a
random one would be wrong. Dropping the default also makes `id` required when
you insert, which is what you want here.

```typescript
id: uuidPrimaryId({ defaultRandom: false }).references(() => authUsers.id, {
  onDelete: "cascade",
  onUpdate: "cascade",
})
```

```sql
"id" uuid PRIMARY KEY
-- foreign key emitted as a separate statement:
ALTER TABLE "profiles" ADD CONSTRAINT "profiles_id_users_id_fkey"
  FOREIGN KEY ("id") REFERENCES "auth"."users"("id")
  ON DELETE CASCADE ON UPDATE CASCADE;
```

`sequentialPrimaryId()` takes the three axes of the Postgres identity column it
builds, which is where the option names come from:

| Option | Values | Default | What it changes |
|---|---|---|---|
| `type` | `"bigint"`, `"integer"` | `"bigint"` | `integer` stops at 2.1 billion rows. |
| `mode` | `"number"`, `"bigint"` | `"number"` | The TypeScript type. `bigint` only. |
| `generated` | `"byDefault"`, `"always"` | `"byDefault"` | `always` refuses client-supplied ids. |

`mode` defaults to `"number"` because PostgREST serialises to JSON numbers, so
`"bigint"` would put your Drizzle type at odds with the types Supabase
generates. It applies to `bigint` only, and passing it alongside
`type: "integer"` is a type error.

`assignedPrimaryId({ length })` bounds the column:

```typescript
id: assignedPrimaryId({ length: 32 }) // "id" varchar(32) PRIMARY KEY
```

All three take `name` when the column isn't called `id`.

### Columns

_Slot ②: in the columns map._ Utils that create commonly-used columns so you
don't redeclare them on every table. All of them are functions you call at each
use site, and they come in two shapes.

**Ready-made columns** have fixed database names. Spread a group into your column
map (`...auditColumns()`), or assign a single column to a key. Every call returns
fresh Drizzle column builders, so customising a column on one table can never
reach another table built from the same helper.

`timestamps()` adds `createdAt` and `updatedAt`:

```typescript
...timestamps()
// createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow()
// updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow()
```

```sql
"created_at" timestamp with time zone DEFAULT now() NOT NULL,
"updated_at" timestamp with time zone DEFAULT now() NOT NULL
```

It takes `withTimezone` (default `true`) and `precision` (0 to 6), and
`auditColumns()` forwards them.

<Callout type="warn">
  **`updated_at` needs a trigger, and so does `updated_by`.** Both get a
  `DEFAULT`, which Postgres applies on insert; SQL has no "on update" default,
  so without a trigger they keep their insert value forever. Adding it is a
  required step for `timestamps()` and `auditColumns()`, covered next.
</Callout>

#### Keeping the update columns current

`created_at` and `created_by` are column `DEFAULT`s, so Postgres fills them for
every writer. `updated_at` and `updated_by` have no equivalent, so they need a
trigger, and that trigger is **required** for the values to mean anything.

Drizzle offers a `$onUpdateFn` hook for this and Zeno deliberately does not use
it. It is applied while Drizzle builds its own statement, so a write arriving
through PostgREST (the `supabase-js` client, the dashboard, any REST caller)
never runs it, and in a Supabase app that is most writes. A column that is
right only when you happen to write through Drizzle is worse than one you know
needs a trigger.

Drizzle Kit generates no trigger DDL, but `drizzle-kit generate --custom` writes
an **empty but tracked** migration (its snapshot links into the chain, so
`db:migrate` applies and records it like any generated one), and
`@zeno-lib/db/triggers` gives you the SQL to put in it.

```bash
pnpm db:generate --custom --name=posts_audit_triggers
```

```typescript
import { auditTriggers } from "@zeno-lib/db/triggers"
import { posts } from "./schemas/posts"

console.log(auditTriggers(posts))
```

Paste the output into the generated migration:

```sql title="{project}-db/supabase/migrations/<timestamp>_posts_audit_triggers.sql"
create extension if not exists moddatetime with schema "extensions";

drop trigger if exists "handle_updated_at" on "public"."posts";
create trigger "handle_updated_at"
  before update on "public"."posts"
  for each row
  execute function "extensions".moddatetime ("updated_at");

create or replace function "public"."set_updated_by"()
  returns trigger
  language plpgsql
  security invoker
  set search_path = ''
as $$
begin
  new."updated_by" = (select auth.uid());
  return new;
end;
$$;

drop trigger if exists "handle_updated_by" on "public"."posts";
create trigger "handle_updated_by"
  before update on "public"."posts"
  for each row
  execute function "public"."set_updated_by"();
```

| Export | Covers |
|---|---|
| `auditTriggers(table, options?)` | Both of the below, matching `auditColumns()`. |
| `updatedAtTrigger(table, options?)` | `updated_at`, for `timestamps()`. |
| `updatedByTrigger(table, options?)` | `updated_by`, for `authorship()`. |

Each reads the table's real name and schema, accepts a plain table name, and
takes `column`, `name` and `schema` overrides. The SQL is re-runnable
(`if not exists`, `drop ... if exists`, `create or replace`), so regenerating a
migration is safe. A write with no session records `NULL` in `updated_by`,
because that is what `auth.uid()` returns for the admin and `service_role`
clients.

**Column builders** take their column name from the key you assign them to, or
from the `name` option.

`authUserId(options?)` is a nullable UUID column referencing `auth.users.id`:

```typescript
userId: authUserId()                              // name from the key → "user_id"
ownerId: authUserId({ name: "owner_id" })         // explicit column name
userId: authUserId({ notNull: true })             // required, ON DELETE RESTRICT
```

```sql
"user_id" uuid
-- foreign key emitted as a separate statement:
ALTER TABLE "<table>" ADD CONSTRAINT "<table>_user_id_users_id_fkey"
  FOREIGN KEY ("user_id") REFERENCES "auth"."users"("id")
  ON DELETE SET NULL ON UPDATE CASCADE;
```

`userId(reference, options?)` is the same column against your own table, which
is the common case once you have a `profiles` mirror:

```typescript
ownerId: userId(() => profiles.id, { notNull: true })
```

<Callout type="warn">
  An **ownership** column that an RLS policy keys on wants `notNull: true`.
  `authUserOwns` builds `owner_column = auth.uid()`, which is `NULL` rather than
  `true` for a null owner, so the row is invisible and cannot be inserted.
  Nullable is right for an audit trail and wrong for ownership.
</Callout>

### RLS policies

_Slot ③: return them from the extra callback._ Wrappers over Drizzle's
`pgPolicy` so you don't hand-write the `for` operation or the owner check at
every call site. Like the rest of this module they are optional: reach for
`policy(...)` or Drizzle's `pgPolicy` directly when you need full control.

**Operation-scoped policies** preset the policy's `for` operation. Each takes
`(name, config?)`, and `config` accepts the usual Drizzle policy options (`to`,
`using`, `withCheck`, `as`). With no `to`, Postgres applies the policy to
`public`:

```typescript
selectPolicy("posts_read", { using: authUserOwns(t.userId) })
// pgPolicy("posts_read", { for: "select", using: ... })
```

```sql
CREATE POLICY "posts_read" ON "posts" AS PERMISSIVE FOR SELECT TO public
  USING ("posts"."user_id" = (select auth.uid()));
```

These helpers only preset `for`; you still supply the condition. Postgres
accepts it in a different clause per operation:

| Export | `for` | Condition goes in |
|---|---|---|
| `selectPolicy(name, config?)` | `SELECT` | `using` |
| `insertPolicy(name, config?)` | `INSERT` | `withCheck` |
| `updatePolicy(name, config?)` | `UPDATE` | `using` + `withCheck` |
| `deletePolicy(name, config?)` | `DELETE` | `using` |
| `allPolicy(name, config?)` | `ALL` | `using` + `withCheck` |
| `policy(name, config)` | raw `pgPolicy`, you set `for` yourself | n/a |

`authUserOwns(ownerColumn)` is not a policy but the condition most of them use,
the SQL fragment for composing `using` / `withCheck`:

```typescript
authUserOwns(t.userId) // sql`${t.userId} = ${authUid}`
```

```sql
"posts"."user_id" = (select auth.uid())
```

**Authenticated policies** sit between the two: they preset `TO authenticated`,
which every hand-written policy repeats, and leave the condition to you. Reach
for these whenever access depends on more than the row's own owner column.

```typescript
authenticatedSelectPolicy("posts_read", { using: sql`is_published(posts.id)` })
```

```sql
CREATE POLICY "posts_read" ON "posts" AS PERMISSIVE FOR SELECT
  TO "authenticated" USING (is_published(posts.id));
```

| Export | `for` | Condition goes in |
|---|---|---|
| `authenticatedSelectPolicy(name, config?)` | `SELECT` | `using` |
| `authenticatedInsertPolicy(name, config?)` | `INSERT` | `withCheck` |
| `authenticatedUpdatePolicy(name, config?)` | `UPDATE` | `using` + `withCheck` |
| `authenticatedDeletePolicy(name, config?)` | `DELETE` | `using` |
| `authenticatedAllPolicy(name, config?)` | `ALL` | `using` + `withCheck` |

**Function policies** cover the case those still leave verbose. Once access
depends on anything but the row's own owner column, the usual answer is a
`security definer` function, which is also the standard advice for keeping RLS
predicates out of the planner's way. `functionPolicies(columns, options?)`
writes all four:

```typescript
export const posts = table("posts", { id: primaryId("uuid") }, (t) =>
  functionPolicies(t, { argument: t.id })
)
```

```sql
CREATE POLICY "can_select_posts" ON "posts" AS PERMISSIVE FOR SELECT
  TO "authenticated" USING ((select "can_select_posts"("posts"."id")));
CREATE POLICY "can_insert_posts" ON "posts" AS PERMISSIVE FOR INSERT
  TO "authenticated" WITH CHECK ((select "can_insert_posts"("posts"."id")));
CREATE POLICY "can_update_posts" ON "posts" AS PERMISSIVE FOR UPDATE
  TO "authenticated" USING ((select "can_update_posts"("posts"."id")))
  WITH CHECK ((select "can_update_posts"("posts"."id")));
CREATE POLICY "can_delete_posts" ON "posts" AS PERMISSIVE FOR DELETE
  TO "authenticated" USING ((select "can_delete_posts"("posts"."id")));
```

It puts the condition in the clause each operation takes: `using` for select and
delete, `withCheck` for insert, both for update. The call is wrapped in a
`select` so Postgres evaluates it once per statement rather than once per row,
the same shape `auth.uid()` uses.

| Option | Default | What it changes |
|---|---|---|
| `argument` | none | Column passed to each function. Omit for functions that take none. |
| `prefix` | `"can"` | Start of the generated function and policy names. |
| `name` | `(operation, table) => …` | Overrides the policy name only. |

It takes the columns object the extra callback gives you (`t`), not the table,
because naming a table inside its own definition makes its type circular. The
table name comes from the columns, so it stays right through a rename.

You write the functions themselves; Zeno only writes the policies that call
them.

**Owner policies** are the narrowest preset: they force `TO authenticated` and
default the owner check to `authUserOwns(ownerColumn)`. Each takes `(name, ownerColumn,
config?)`; pass `using` or `withCheck` to override.

```typescript
authenticatedOwnerSelectPolicy("posts_owner_select", t.userId)
```

```sql
CREATE POLICY "posts_owner_select" ON "posts" AS PERMISSIVE FOR SELECT
  TO "authenticated" USING ("posts"."user_id" = (select auth.uid()));
```

| Export | `for` | Owner check applied to |
|---|---|---|
| `authenticatedOwnerSelectPolicy` | `SELECT` | `using` |
| `authenticatedOwnerInsertPolicy` | `INSERT` | `withCheck` |
| `authenticatedOwnerUpdatePolicy` | `UPDATE` | `using` + `withCheck` |
| `authenticatedOwnerDeletePolicy` | `DELETE` | `using` |
| `authenticatedOwnerAllPolicy` | `ALL` | `using` + `withCheck` |

### Supabase primitives

Re-exported from `drizzle-orm/supabase` so roles, the `auth.users` table, and
helpers all come from one Zeno-owned entrypoint. Reference these; do not
redeclare Supabase's built-in roles in your schema.

| Export | What it is |
|---|---|
| `anonRole` | The `anon` (unauthenticated) role. |
| `authenticatedRole` | The `authenticated` (signed-in user) role. |
| `serviceRole` | The `service_role` (RLS-bypassing) role. |
| `postgresRole` | The `postgres` superuser role. |
| `supabaseAuthAdminRole` | The `supabase_auth_admin` role that owns the auth schema. |
| `authUid` | The `auth.uid()` SQL helper for the current user id. |
| `realtimeMessages` | The Supabase Realtime `messages` table. |
| `realtimeTopic` | The `realtime.topic()` SQL helper. |

### auth.users

`auth.users` comes from a **separate** entrypoint, `@zeno-lib/db/auth`:

```typescript
import { authUsers } from "@zeno-lib/db/auth"
```

It is the full 35-column table, generated with `drizzle-kit pull` and pinned to
Supabase CLI 2.84.1 / GoTrue v2.188.1. Drizzle's own `drizzle-orm/supabase`
export has 8 of those columns, so putting `auth` in `schemaFilter` made
drizzle-kit want to drop the other 27, and anyone needing a foreign key into
`auth.users` hand-wrote the table instead.

<Callout type="warn">
  The reason it has its own entrypoint is that `drizzle-kit generate` applies
  **no** entity filter: it passes `() => true`, and its config accepts neither
  `schemaFilter` nor `entities`. So neither `pgSchema("auth").existing()` nor a
  `schemaFilter` in your drizzle config stops it emitting
  `CREATE TABLE "auth"."users"`. The only thing that does is the table never
  reaching the files your `schema` glob reads.

  Import it in queries. Do **not** re-export it from the
  `{project}-db/src/schema.ts` barrel your `drizzle.config.ts` points at, or the
  next `drizzle-kit generate` will try to create a table Supabase already owns.
  Referencing it from a column (`authUserId()`) is always safe: a table reached
  only through a `references()` thunk is never collected.
</Callout>

Several columns hold credential material (`encryptedPassword`, the `*Token`
columns), and reading the table at all needs an RLS-bypassing client. Select the
columns you need rather than `select()`:

```typescript
import { createAdminClient } from "@zeno-lib/db"
import { authUsers } from "@zeno-lib/db/auth"

const db = createAdminClient()
const users = await db
  .select({ email: authUsers.email, lastSignInAt: authUsers.lastSignInAt })
  .from(authUsers)
```

The nine `auth` enums are deliberately not shipped. `auth.users` uses none of
them (they belong to the `mfa_*`, `oauth_*` and `sso_*` tables), and drizzle-kit
never filters enums, so an exported one would be `CREATE TYPE` in every command.

### pg-core aliases

Curated aliases over `drizzle-orm/pg-core` so schema files don't repeat the `pg`
prefix at every call site. They behave exactly like their Drizzle counterparts.
(`schema` is the one exception and has its own section above, because it applies
casing and RLS where `pgSchema` applies neither.)

| Alias | Drizzle export |
|---|---|
| `enum` | `pgEnum` |
| `view` | `pgView` |
| `materializedView` | `pgMaterializedView` |
| `sequence` | `pgSequence` |
| `role` | `pgRole` |
| `tableCreator` | `pgTableCreator` |
| `isEnum` | `isPgEnum` |
| `isView` | `isPgView` |
| `isMaterializedView` | `isPgMaterializedView` |
| `isSchema` | `isPgSchema` |
| `isSequence` | `isPgSequence` |

## Pitfalls

- Use `table` for user-scoped application tables so RLS is enabled by default.
- Use `unsecureTable` only when the table is intentionally not protected by
  RLS.
- Do not hand-write RLS policies in migration files when the table is otherwise
  managed by Drizzle. Put `policy(...)`, `selectPolicy(...)`, or owner policy
  helpers in the schema and generate the migration.
- Do not manually declare Supabase's built-in roles; import the existing role
  exports from `@zeno-lib/db/schema`.
