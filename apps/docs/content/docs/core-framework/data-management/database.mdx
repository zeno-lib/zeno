Zeno uses [Supabase Postgres](https://supabase.com/database) for the database
and [Drizzle](https://orm.drizzle.team/docs/sql-schema-declaration) for
type-safe schema definitions, migrations, and server-side queries. The
`@zeno-lib/db` package ties those pieces together so an app can define tables in
TypeScript, generate SQL migrations, and run queries with Supabase Row Level
Security (RLS) applied correctly.

This guide starts from the first table. You do not need to have used Drizzle,
RLS, or `@zeno-lib/db` before.

## What you get

Adding `@zeno-lib/db` gives you a small Supabase-ready layer around Drizzle:

| Import | What it provides |
|---|---|
| `@zeno-lib/db` | `createSupabaseDrizzle(...)`, the client factory for admin queries and RLS-aware queries. |
| `@zeno-lib/db/config` | `defineDrizzleConfig(...)`, the Drizzle Kit preset for Supabase projects. |
| `@zeno-lib/db/schema` | `dbTable`, `unsecureDbTable`, Supabase roles/helpers, and `timestamps` for schema files. |
| `@zeno-lib/db/clients` | Lower-level admin/RLS client factories for shared libraries that need explicit client control. |

<Callout type="warn">
`@zeno-lib/db` runtime clients are server-only. They use `postgres-js`, which
opens TCP connections to Postgres. Browser code should call Server Actions or
Route Handlers that use this package for application data.
</Callout>

## Concepts

### Supabase Postgres

Every Supabase project includes a Postgres database. You can query it directly
from trusted server code, and Supabase can also expose it through APIs such as
PostgREST and Supabase client libraries.

The important security rule is: user-scoped tables need
[Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).
RLS is a Postgres feature that attaches policies to tables. You can think of a
policy as database-level authorization logic that Postgres applies whenever a
role tries to read, insert, update, or delete rows.

Supabase requests run as database roles. The two roles you use most often are:

- `anon`: an unauthenticated request. Use this for data that can be read or
  written without a signed-in user, if your app allows that.
- `authenticated`: a request with a valid signed-in Supabase user. Use this for
  data that depends on who the user is.

Inside RLS policies, Supabase helpers expose information about the current
request:

- [`auth.uid()`](https://supabase.com/docs/guides/database/postgres/row-level-security#authuid)
  returns the current user's id.
- [`auth.jwt()`](https://supabase.com/docs/guides/database/postgres/row-level-security#authjwt)
  returns the current user's JWT claims. Use trusted app metadata for
  authorization data, not user-editable metadata.

### Drizzle

[Drizzle schema files](https://orm.drizzle.team/docs/sql-schema-declaration)
let you declare Postgres tables in TypeScript. Those declarations become the
types you use in application queries.

[Drizzle Kit migrations](https://orm.drizzle.team/docs/migrations) read those
schema files, generate SQL migration files, and apply them to the database. In
Zeno, the normal workflow is codebase-first: update the TypeScript schema,
generate migrations, review the generated SQL, and apply it.

Drizzle also supports
[RLS policies](https://orm.drizzle.team/docs/rls), including Supabase's built-in
roles and helpers.

## Installation

Install the database package in the package or app that owns your schema:

```npm
pnpm add @zeno-lib/db drizzle-orm@1.0.0-rc.3 postgres
pnpm add -D drizzle-kit@1.0.0-rc.3 dotenv
```

`dotenv` is only needed by scripts and config files that run outside your
framework runtime, such as `drizzle.config.ts`. Next.js and Vercel expose
environment variables to server runtime code, but a standalone Drizzle Kit CLI
process needs you to load local `.env` files yourself.

## Define your schema

Start with a TypeScript schema. Drizzle Kit reads exported tables from this file
when it generates migrations, and Drizzle uses the same exported table objects
when you write queries.

```typescript lineNumbers title="src/schema.ts"
import {
  authenticatedRole,
  authUid,
  authUsers,
  dbTable,
  timestamps,
} from "@zeno-lib/db/schema"
import { sql } from "drizzle-orm"
import { pgPolicy, text, uuid } from "drizzle-orm/pg-core"

export const posts = dbTable(
  "posts",
  {
    id: uuid("id").primaryKey().defaultRandom(),
    title: text().notNull(),
    userId: uuid()
      .notNull()
      // Supabase owns auth.users; this reference links your table to the signed-in user.
      .references(() => authUsers.id),
    // Reusable created_at and updated_at columns from @zeno-lib/db/schema.
    ...timestamps,
  },
  (t) => [
    pgPolicy("posts_owner_select", {
      for: "select",
      to: authenticatedRole,
      using: sql`${t.userId} = ${authUid}`,
    }),
    pgPolicy("posts_owner_insert", {
      for: "insert",
      to: authenticatedRole,
      withCheck: sql`${t.userId} = ${authUid}`,
    }),
  ]
)

export type InsertPost = typeof posts.$inferInsert
export type SelectPost = typeof posts.$inferSelect
```

`dbTable` is Zeno's default table helper. It uses Drizzle's snake_case table
builder, so TypeScript properties like `userId` become database identifiers like
`user_id`, and it enables RLS by default. Use `unsecureDbTable` only for tables
that intentionally should not have RLS, such as seed-only reference data.

The imports from `@zeno-lib/db/schema` are Zeno's Supabase schema conveniences:

- `dbTable` - RLS-ready, snake_case Postgres table builder.
- `authUsers` - Drizzle's model of Supabase's existing `auth.users` table.
- `authenticatedRole` - Supabase's existing `authenticated` database role.
- `authUid` - SQL helper for `auth.uid()`.
- `timestamps` - reusable `created_at` and `updated_at` columns.

Keeping this shape in TypeScript has a few practical benefits: the table is the
source of truth for migrations, query types are inferred from the same object,
common columns can be reused as code, and validation schemas can be derived from
the table later. For that next layer, see
[Schemas](/docs/core-framework/data-management/schemas).

## Clients

Both runtime clients and the Drizzle Kit preset read `DATABASE_URL` from the
environment unless you pass an explicit `connectionString` override.

For local Supabase:

```dotenv
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

For deployed Supabase projects, prefer the
[Supabase connection pooler](https://supabase.com/docs/guides/database/connecting-to-postgres#server-side-poolers)
for serverless or autoscaling environments. The package sets `prepare: false` on
the underlying `postgres-js` pools so Supabase's transaction-mode pooler works.

Create the request-scoped Supabase client first, then bind it to
`createSupabaseDrizzle(...)`:

```typescript title="route.ts"
import { createSupabaseDrizzle } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import * as schema from "./schema"
import { posts } from "./schema"

const supabase = await createClient()
const db = createSupabaseDrizzle({ schema, supabase })

const mine = await db.rls((rlsDb) => rlsDb.select().from(posts))
```

Pass the imported schema module object to `createSupabaseDrizzle(...)`. Do not
build a new schema object inline for each request; reusing the module import
lets `@zeno-lib/db` reuse its underlying Postgres pools safely.

`createSupabaseDrizzle(...)` reads `DATABASE_URL` from the server environment in
this example. You only need `connectionString` when a script or service
intentionally connects to a different database URL.

## Configure Drizzle Kit

Create a
[`drizzle.config.ts`](https://orm.drizzle.team/docs/drizzle-config-file) next to
the package or app that owns the schema:

```typescript title="drizzle.config.ts"
import "dotenv/config"
import { defineDrizzleConfig } from "@zeno-lib/db/config"

export default defineDrizzleConfig()
```

Keep `import "dotenv/config"` here. Next.js loads `.env*` files for code running
inside the Next runtime, and Vercel provides environment variables during builds
and function execution, but Drizzle Kit runs this config as its own CLI process.
The import makes local `.env` values available before `defineDrizzleConfig()`
reads `process.env.DATABASE_URL`.

The preset:

- Reads schema from `./src/schema.ts`.
- Writes migrations to `./supabase/migrations`.
- Uses the `postgresql` dialect.
- Reads `DATABASE_URL`.
- Keeps Supabase's built-in roles marked as existing.

You can still pass Drizzle Kit overrides for package-specific paths or
credentials:

```typescript title="drizzle.config.ts"
import "dotenv/config"
import { defineDrizzleConfig } from "@zeno-lib/db/config"

export default defineDrizzleConfig({
  dbCredentials: {
    url: process.env.MIGRATIONS_DATABASE_URL ?? "",
  },
  schema: "./src/db/schema.ts",
})
```

## Generate migrations

Recommended package scripts:

```json title="package.json"
{
  "scripts": {
    "dev": "pnpm exec supabase start",
    "stop": "pnpm exec supabase stop",
    "reset": "pnpm exec supabase db reset && pnpm db:seed",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "drizzle-kit migrate",
    "db:seed": "node src/seed.ts"
  }
}
```

What each script does:

- `dev` starts your local Supabase stack, including local Postgres.
- `stop` stops the local Supabase stack.
- `reset` rebuilds the local database from migration files, then runs your seed
  script.
- `db:generate` reads your TypeScript schema and writes a SQL migration under
  `supabase/migrations`.
- `db:migrate` applies generated migrations to a database and records them in
  Drizzle Kit's migration table.
- `db:seed` runs your project-owned seed script.

Author tables and RLS policies in your Drizzle schema, run
`drizzle-kit generate`, review the generated SQL, and commit the generated SQL
under `supabase/migrations`. Apply generated migrations with
`drizzle-kit migrate` in environments where the database is not reset from
scratch.

## Query with RLS

Every user-scoped query should run inside `db.rls(...)`.

```typescript title="route.ts"
import { createSupabaseDrizzle } from "@zeno-lib/db"
import { createClient } from "@zeno-lib/supabase/server"
import * as schema from "./schema"
import { posts } from "./schema"

const supabase = await createClient()
const db = createSupabaseDrizzle({ schema, supabase })

const mine = await db.rls((rlsDb) => rlsDb.select().from(posts))
```

`db.rls(...)` calls `supabase.auth.getClaims()` before the transaction. Supabase
returns a verified JWT payload, and the package installs those claims into
transaction-local Postgres settings so helpers like `auth.uid()` and
`auth.jwt()` work inside RLS policies.

The RLS role is limited to `anon` or `authenticated`. Unknown role claims fall
back to `anon`, and `service_role` never runs through the request-scoped RLS
path.

Calling `db.rls(...)` without passing `supabase` to
`createSupabaseDrizzle(...)` throws immediately, so missing auth context does
not silently become an anon query.

## Use admin queries carefully

For trusted server work that should bypass user RLS, omit the `supabase` option
and use `db.admin`:

```typescript title="seed.ts"
import { createSupabaseDrizzle } from "@zeno-lib/db"
import * as schema from "./schema"
import { posts } from "./schema"

const db = createSupabaseDrizzle({ schema })

await db.admin.select().from(posts)
```

`db.admin` is appropriate for seed scripts, webhooks, cron jobs, admin tools,
and background jobs. It should not be used for user-scoped reads or writes.

## Lower-level clients

Most apps should use `createSupabaseDrizzle(...)`. If a shared library needs
explicit control over clients, use `createDrizzleClients(...)`:

```typescript lineNumbers
import { createDrizzleClients } from "@zeno-lib/db/clients"
import * as schema from "./schema"

const clients = createDrizzleClients({ schema })
const admin = clients.getDrizzleSupabaseAdminClient()
const rls = clients.getDrizzleSupabaseClient({
  role: "authenticated",
  sub: "00000000-0000-0000-0000-000000000000",
})

const rows = await rls.runTransaction((rlsDb) =>
  rlsDb.select().from(schema.posts)
)

await clients.closeDrizzleSupabaseClients()
```

When using the lower-level RLS client, pass a Supabase client whenever possible.
If you pass claims directly, they must already be verified. The DB package does
not decode or trust raw JWT strings.

## Common pitfalls

- Do not import `@zeno-lib/db` runtime clients from Client Components or browser
  code.
- Use `dbTable` for user-scoped application tables so RLS is enabled by default.
- Use `unsecureDbTable` only when the table is intentionally not protected by
  RLS.
- Do not use `db.admin` for user-scoped reads and writes.
- Do not pass raw access token strings or unverified session payloads to RLS
  helpers.
- Do not hand-write RLS policies in migration files when the table is otherwise
  managed by Drizzle. Put `pgPolicy(...)` in the schema and generate the
  migration.
- Do not manually declare Supabase's built-in roles; import the existing role
  exports from `@zeno-lib/db/schema`.
- Do not remove `entities.roles.provider: "supabase"` from Drizzle Kit config,
  or generated migrations may try to create or drop Supabase-managed roles.
- Do not create fresh schema object literals per request.
- Do not run queries outside `db.rls(...)` when you expect RLS policies to
  apply.
