The `@zeno-lib/supabase` package is a thin wrapper around [`@supabase/ssr`](https://supabase.com/docs/guides/auth/server-side/nextjs) for the Next.js App Router. It provides the browser, server, and middleware client factories — wired with the cookie handling that SSR auth needs — plus a `next/image` loader for Supabase Storage. The value is in keeping the client / server / middleware split honest so your auth session stays in sync across navigations.

## What you get

Each concern is its own entry point, so you only pull in the client that matches where your code runs.

| Import | Use from | Provides |
|---|---|---|
| `@zeno-lib/supabase/client` | Client Components, browser code | `createClient` (browser) + `EmailOtpType`, `QueryData`, `SupabaseClient` type re-exports |
| `@zeno-lib/supabase/server` | Server Components, Route Handlers, Server Actions | `createClient` (server, **async**) |
| `@zeno-lib/supabase/next-middleware` | App `middleware.ts` | Ready-made `middleware` + static `config`, plus the `createMiddleware(options)` factory |
| `@zeno-lib/supabase/supabase-middleware` | Custom middleware compositions | `updateSession(request, options?)` — configurable cookie-refresh + auth-gate logic |
| `@zeno-lib/supabase/image-loader` | A local `next/image` loader file | `supabaseImageLoader` + `createSupabaseImageLoader(options?)` — Storage transformation URL builder |

## Installation

### 1. Install the packages

Install `@zeno-lib/supabase` alongside its Supabase peer dependencies. `next` (>= 16) is an optional peer — only the `server`, `next-middleware`, and `supabase-middleware` entry points import it, and your app already ships it:

```npm
npm install @zeno-lib/supabase @supabase/ssr @supabase/supabase-js
```

### 2. Set the environment variables

The factories read their configuration from public environment variables:

| Variable | Used by | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `client`, `server`, `supabase-middleware` | Required. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | `client`, `server`, `supabase-middleware` | Required. |
| `NEXT_PUBLIC_SUPABASE_STORAGE_PROJECT_ID` | `image-loader` | Falls back to `NEXT_PUBLIC_SUPABASE_PROJECT_ID`. |

```bash title=".env"
NEXT_PUBLIC_SUPABASE_URL=https://<project-id>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<your-anon-key>
```

<Callout type="info">
The `client` and `server` factories accept explicit `(supabaseUrl, supabaseKey)` arguments, and `updateSession` accepts the same through its options — all take precedence over the env vars. If neither side supplies both values, the call throws `Missing Supabase … environment variables`.
</Callout>

## Browser client

Use `@zeno-lib/supabase/client` from Client Components and any other browser-side code:

```tsx title="app/_components/profile.tsx"
"use client"

import { createClient } from "@zeno-lib/supabase/client"

export function Profile() {
  const supabase = createClient<Database>() // the Database generic is optional

  // supabase.auth, supabase.from(...), ...
}
```

The optional `Database` generic is the type generated by the [`supabase` CLI](https://supabase.com/docs/guides/api/rest/generating-types) — pass it to get fully typed queries, or omit it entirely.

## Server client

`@zeno-lib/supabase/server` reads cookies through `next/headers`, so its `createClient` is **async** and must be awaited. Use it from Server Components, Route Handlers, and Server Actions:

```tsx title="app/page.tsx"
import { createClient } from "@zeno-lib/supabase/server"

export default async function Page() {
  const supabase = await createClient<Database>()
  const {
    data: { user },
  } = await supabase.auth.getUser()

  return <p>{user ? `Hello ${user.email}` : "Not signed in"}</p>
}
```

## Middleware

Middleware refreshes the auth session on every request and gates unauthenticated traffic. The fastest setup is to re-export the ready-made middleware:

```typescript title="middleware.ts"
export { middleware, config } from "@zeno-lib/supabase/next-middleware"
```

The bundled `config.matcher` already skips static assets and image files.

To change the redirect target or the public (auth-exempt) routes, build the middleware with `createMiddleware`. Next requires `config.matcher` to be statically analyzable, so keep a static `config` export alongside it (re-export the default or declare your own):

```typescript title="middleware.ts"
import { createMiddleware, config } from "@zeno-lib/supabase/next-middleware"

export const middleware = createMiddleware({
  // /sign-in is already the default; add the other public routes
  publicPaths: ["/sign-in", "/sign-up", "/auth", "/recover-password"],
})
export { config }
```

For full control, call `updateSession(request, options?)` inside your own middleware:

```typescript title="middleware.ts"
import { type NextRequest } from "next/server"
import { updateSession } from "@zeno-lib/supabase/supabase-middleware"

export async function middleware(request: NextRequest) {
  // ...your logic that does not touch the Supabase response...
  return await updateSession(request)
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

### Redirect defaults

The middleware **defaults** to redirecting unauthenticated users to `/sign-in` and treating `/sign-in` and `/auth` as public — matching the [`@zeno-lib/authentication`](https://www.npmjs.com/package/@zeno-lib/authentication) package's `/sign-in` UI, so the two work together with no configuration.

Since only `/sign-in` and `/auth` are public by default, pass `signInPath` and `publicPaths` to `createMiddleware` / `updateSession` (above) when your routes differ — e.g. add `/sign-up` and `/recover-password` so those flows stay reachable.

<Callout type="warn">
`signInPath` must itself be listed in `publicPaths`, or unauthenticated users hit an infinite redirect loop (they get sent to the sign-in page, which then redirects again). The defaults keep this in sync.
</Callout>

## Storage image loader

`@zeno-lib/supabase/image-loader` builds [Supabase Storage transformation URLs](https://supabase.com/docs/guides/storage/serving/image-transformations#nextjs-loader) for `next/image`. Next's `images.loaderFile` must point at a **project-relative file with a default export**, and `supabaseImageLoader` is a named export, so add a one-line wrapper:

```typescript title="image-loader.ts"
export { supabaseImageLoader as default } from "@zeno-lib/supabase/image-loader"
```

```javascript title="next.config.mjs"
export default {
  images: { loader: "custom", loaderFile: "./image-loader.ts" },
}
```

When the project id isn't available via environment variables at import time, build the loader explicitly with `createSupabaseImageLoader({ projectId })` and default-export the result.

`http(s)` sources pass through untouched; relative paths are rewritten to `https://<projectId>.supabase.co/storage/v1/object/public/<src>?width=<w>&quality=<q|75>`.

## Types

The few `@supabase/supabase-js` types you actually need are re-exported from `@zeno-lib/supabase/client`, so you can import them in one place instead of depending on `@supabase/supabase-js` directly:

```typescript
import type {
  EmailOtpType,
  QueryData,
  SupabaseClient,
} from "@zeno-lib/supabase/client"
```
